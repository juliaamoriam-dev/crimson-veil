# Regras do Workspace — Crimson Veil

1. Crimson Veil é um projeto de software de longo prazo. Priorize organização, manutenção, escalabilidade e qualidade do código.

2. Sempre analise a estrutura existente do projeto e os arquivos relevantes antes de implementar alterações.

3. Não crie arquivos, componentes, classes, serviços ou funcionalidades duplicadas quando uma implementação existente puder ser reutilizada ou expandida.

4. Mantenha frontend, backend, banco de dados, configurações e documentação devidamente organizados e separados.

5. Siga a arquitetura e a stack tecnológica definidas na documentação oficial do projeto.

6. Não adicione dependências ou tecnologias sem necessidade real e justificativa.

7. Nunca armazene senhas, tokens, chaves de API ou credenciais diretamente no código.

8. Utilize variáveis de ambiente ou mecanismos apropriados de configuração para informações sensíveis e específicas de cada ambiente.

9. Valide entradas e trate erros de maneira adequada.

10. Alterações no banco de dados devem ser intencionais, controladas e documentadas.

11. Nunca altere ou exclua estruturas ou dados do banco de maneira casual.

12. Os contratos da API devem permanecer consistentes entre frontend e backend.

13. Utilize nomes claros, descritivos e consistentes para variáveis, métodos, classes, componentes, endpoints e entidades.

14. Evite otimizações prematuras e abstrações desnecessárias.

15. Não reescreva código funcional apenas para aplicar outro estilo ou padrão.

16. Alterações que afetem arquitetura, banco de dados, contratos da API, autenticação ou estruturas importantes da interface devem ser explicadas antes da implementação.

17. Mantenha cada alteração focada e fácil de revisar.

18. Após implementar uma alteração, teste ou verifique as funcionalidades afetadas.

19. Quando houver incerteza, não invente uma solução silenciosamente. Informe a dúvida e apresente opções.

20. Preserve a integridade do universo de Crimson Veil. Não crie personagens, casos, locais, organizações, relações ou acontecimentos oficiais sem aprovação explícita.

21. O projeto deve utilizar português como idioma padrão em código, documentação, interface, mensagens, comentários e nomenclaturas, salvo quando houver uma razão técnica para utilizar outro idioma.

22. O código deve priorizar clareza para uma desenvolvedora brasileira que está aprendendo Engenharia de Software.

23. Sempre que uma decisão técnica importante for tomada, explique o conceito de forma didática quando isso contribuir para o aprendizado da desenvolvedora.

24. Utilize práticas próximas de um projeto profissional, mas evite complexidade empresarial desnecessária durante o desenvolvimento do MVP.

25. Uma funcionalidade não deve ser considerada concluída apenas porque o código compila. Seu comportamento esperado deve ser verificado.

26. Organize o projeto para que outra pessoa desenvolvedora consiga compreender sua estrutura e continuar o desenvolvimento.

27. Antes de realizar alterações grandes ou estruturais, apresente um resumo do que será alterado e o motivo.

28. Nunca remova funcionalidades, arquivos ou dados existentes sem autorização explícita.

29. A documentação do projeto deve acompanhar sua evolução. Alterações relevantes devem refletir-se na documentação correspondente.

30. O sistema deve ser desenvolvido de forma incremental: primeiro funcionamento correto, depois refinamento, otimização e melhorias visuais.
